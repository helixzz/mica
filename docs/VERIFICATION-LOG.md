## 2026-10-22 夜间（v1.71.0 → v1.72.3）

### 发现的缺陷

#### 1. 订单页对合同期次编号的操作会落到错误记录上（v1.71.0）

**现象**：在采购订单页，对一个状态为「计划」的期次点执行，返回 `409 already_paid`。

**原因**：订单页的付款计划**有意**同时显示订单自己的期次与关联合同的期次，但两者**各自独立编号**（订单和合同可以都有「第 3 期」）。查找函数在这份并集里按编号取第一条，于是点订单的第 3 期，拿到的是合同的第 3 期。

**影响面比现象大**：改期次、删期次走同一个查找函数，三者都可能误操作。

**证据**：生产上 7 组编号重叠，其中 PO-2026-0016 / 0017 / 0018 的合同期次已付而订单期次仍是计划状态。

#### 2. 审批中心批准后 PR 卡在「已提交」（v1.72.0）

**现象**：从审批中心批准采购申请，审批实例变成「已批准」，但 PR 仍是「已提交」，无法转为采购订单。

**原因**：把审批结果写回业务对象的代码只存在于 PR 详情页的决策端点里；审批中心用通用端点，只改审批实例。

**形状**：同一件事两个入口，只有一个做完整。

#### 3. 部署重启静默吞掉当天的定时扫描（v1.72.1）

**原因**：APScheduler 的 job 存在内存里，而 scheduler 容器每次部署都重建。落在重启窗口里的 cron 时刻永远不会执行，且不报错、不通知。

**现状**：新增启动后 90 秒的幂等补跑（价格异常扫描、合同到期检查）。根本解是持久化 job store，尚未做。

#### 4. 合同币种不符时被静默忽略（v1.72.3）

**现象**：`POST /contracts` 传 `currency: "HKD"`，返回 201 且存 `CNY`。

**原因**：`ContractCreateIn` 根本没有 currency 字段，Pydantic 把值丢掉。合同币种跟随订单是**正确设计**，问题在于调用方得不到提示。

**修复**：接受该字段，不符时 422 并带两边币种。

### 一条共同的形状

四个缺陷都不是逻辑写错，而是**另一条路没人管**：

- 期次：页面并集显示，查找只按编号
- 审批：两个入口，只有一个写回业务对象
- 定时：内存 store + 频繁重启，没人记录错过什么
- 币种：schema 不收，服务层照旧

**找缺陷时优先问：这件事有没有第二个入口？**
